# 相册发布处理规范（规则固化）

> **当前架构（2026-11-15 起）**：GitHub Pages 存代码 + `content.json`，NAS 存媒体，
> cloudflared 快速隧道把 NAS 的 `/srv/pub` 暴露成公网 HTTPS，页面靠 `base.json` 找 NAS。
> 本项目**已完全不使用 EdgeOne**；旧文档里 EdgeOne Pages / Blob 存储的描述全部作废。
> 本文是**可执行规则**，不是建议。顺序错了结果就是错的。

## 0. 一条数据链，四个环节

```
NAS 共享文件夹 Photos/  原图原片（2.1 GB，永不动）
        │  pub_img.py：烘焙方向 → 去 EXIF → 长边 2048 → q85 → 文件名小写
        ▼
/srv/pub/img/           公网压缩图（562 张，361 MB）
        │  mkthumb.py：长边 720、q78
        ▼
/srv/pub/img/t/         网格缩略图（约 100 KB/张）
        │
/srv/pub/video/         转码 MP4 + video/poster/ 首帧封面
        │  mkindex.py：合并成 index.json（含 t / p 字段）
        ▼
/srv/pub/index.json  ──► build_content.py ──► 仓库 data/content.json
                                                  │
GitHub Pages  ◄── 页面 fetch content.json + base.json ──┘
        ▲
        │  base-sync.sh --watch 300：隧道换域名就推 base.json
cloudflared 快速隧道（Caddy :8443 → /srv/pub）
```

| 仓库里的东西 | NAS 上的东西 |
|---|---|
| HTML / CSS / JS、字体、`data/content.json`、`base.json` | 原片、压缩图、缩略图、转码视频、封面、`index.json` |

**铁律**：`Photos/` 里的文件一个字节都不要改。加工产物只出现在 `album-pub/`（容器内 `/srv/pub`），绝不回写。

## 2. 图片处理：六步，顺序不可调换

iPhone 竖拍的**像素其实是横的**，靠 EXIF `Orientation=6` 让浏览器转 90°。
先清 EXIF 再去方向 = 几百张一起全躺下。所以顺序是死的：

| # | 动作 | 为什么 |
|---|---|---|
| 1 | 读 EXIF 拍摄时间（`36867` → `306` → mtime） | 后面元信息会丢，日期必须提前取 |
| 2 | `ImageOps.exif_transpose(im)` **烘焙方向** | 把 Orientation 写进像素 |
| 3 | 统一 RGB（RGBA/LA/P 白底合成） | 透明通道直接转 JPG 会变黑底 |
| 4 | 长边 **2048**、LANCZOS | 保清晰度；4032px 原图对网页没有意义 |
| 5 | JPEG **q85 + optimize + progressive**，**不传** `exif=` / `icc_profile=` | PIL 不传就不写，等于彻底去元信息 |
| 6 | 文件名统一**小写** `.jpg` | 避免 `IMG_1.JPG` 与 `img_1.jpg` 大小写 404 |

**这里说的「压缩」不是降分辨率到低清**：长边 2048、q85，100% 放大才看得出差别，
省下来的 60–75% 主要来自去掉 EXIF/ICC/缩略图数据和渐进式重编码。

入口：`python3 pub_img.py /srv/csy /srv/pub`

验收：线上图片 `EXIF 条目数 = 0`、`progressive = 1`、尺寸未被压到 1000px 以下。

## 3. 缩略图（网格专用，别拿原图硬扛）

`/srv/pub/img/t/<同名>.jpg`，长边 **720**、q78，约 100 KB/张。

```sh
python3 mkthumb.py /srv/pub --edge 720 --quality 78
```

- 网格、`home` 照片墙、灯箱首屏都用缩略图；**点开灯箱才加载 2048px 压缩原图**。
- `build_content.py` 把 `index.json` 的 `t` 字段写成 `content.json` 的 **`thumb`** 字段。
  早期版本写成 `s`，前端现在 `p.thumb || p.s` 两者都兼容。
- `Site.guardImg` 会在缩略图 404 时自动退回原图并把 `thumbDead` 置真，
  所以「缩略图还没生成」只会慢，不会白屏。

## 4. 视频处理：转码 + 首帧封面

### 4.1 为什么要转码

线上曾直接放手机原码：16 个共 **286 MB**，单个最高 30 MB。
更糟的是首页 3 个 `<video preload="metadata">` 没有 poster，Chromium 会发
`Range: bytes=0-` 的开放式请求，把整个 mp4 拖下来 —— **打开首页就 68.6 MB**。

### 4.2 转码参数

```sh
ffmpeg -y -v error -i in.mp4 \
  -vf "scale=1280:1280:force_original_aspect_ratio=decrease,format=yuv420p" \
  -c:v libx264 -crf 23 -preset veryfast \
  -c:a aac -b:a 96k \
  -movflags +faststart -map_metadata -1 -map_chapters -1 \
  out.mp4
```

| 参数 | 作用 |
|---|---|
| `scale=1280:1280:force_original_aspect_ratio=decrease` | 长边限 1280，竖屏 1080×1920 → 720×1280，横屏自动 1280×720 |
| `format=yuv420p` | 8bit 4:2:0，Chrome/Safari 全兼容 |
| `-movflags +faststart` | moov 前置，网页拖动进度条不用下完整个文件 |
| `-map_metadata -1` | 去掉 GPS 等元信息，和图片口径一致 |

实测 29 MB → 约 2–9 MB（取决于画面复杂度），16 个合计从 286 MB 降到 30–90 MB。

### 4.3 首帧封面（poster）

```sh
ffmpeg -y -v error -ss 1 -i in.mp4 -frames:v 1 \
  -vf "scale=640:640:force_original_aspect_ratio=decrease" \
  -q:v 5 /srv/pub/video/poster/<name>.jpg
```

`mkindex.py` 只在封面文件真实存在时才写 `p` 字段。
前端 `vid.poster` 默认是仓库里的 `assets/img/video-poster.svg`（走 Pages，零请求），
有 `p` 时先 `new Image()` 预检通过才替换，404 就安静保持 SVG。

**前端铁律**：`<video>` 一律 `preload="none"`，且必须有 poster。
`metadata` + 无 poster 会把整段视频拉下来，这个坑已经踩过一次。

### 4.4 HLG HDR 特例

若 `ffprobe` 显示 `color_transfer=arib-std-b67`（iPhone HDR），直接转 H.264 会整体发灰，
需要先做色调映射：

```sh
-vf "zscale=t=linear:npl=100,format=gbrpf32le,zscale=p=bt709,tonemap=tonemap=hable:desat=0,zscale=t=bt709:m=bt709:r=tv,format=yuv420p"
```

当前线上 16 个视频实测是 `bt709 / yuv420p`（已是 SDR），所以用 4.2 的普通链即可。
**不要用 `-c copy` 改封装**：MOV 里的 HEVC 装进 MP4，Chrome 照样播不了。

### 4.5 原片去向

转码前把 `/srv/pub/video` 里的原片**移到** `/var/lib/tailscale/orig_video/`（容器内，不对外），
文件名顺手转小写；`Photos/` 里的原片一个都不动。

## 5. 文件名统一小写

| 位置 | 规则 |
|---|---|
| `/srv/photos` 原图 | 全小写 |
| `/srv/pub/img` 压缩图 | `pub_img.py` 已经强制 `stem.lower() + ".jpg"` |
| `/srv/pub/video` 转码视频 | `img_8205.mp4`，不再是 `IMG_8205.mp4` |
| `video/poster/` 封面 | 与视频同名小写 |
| `data/seed.json` / `data/content.json` | `file` / `src` / `meta.hero` 全小写 |
| `index.json` | `mkindex.py` 输出时 `.lower()` |

`build_content.py` 的 `norm()` 本来就转小写匹配，所以大写不会导致丢数据，
但会让 `meta.hero` 这类**严格 `===` 比较**静默失效（靠 `featured` 兜底，看起来正常，一改就露馅）。
`index.html` 里 hero 匹配已改为 `.toLowerCase()` 双保险。

## 6. 隧道地址自愈

cloudflared **快速隧道**每次重连都会换一个 `xxx.trycloudflare.com` 域名，
所以 `base.json` 里的地址**会变**。这不是 bug，是 quick tunnel 的固有行为。

`base-sync.sh --watch 300` 负责追平：

1. 从 `/var/lib/tailscale/cf.log` 读最新域名；
2. `curl $URL/index.json` 拿到 200 才认为隧道真的就绪（避开 DNS 空窗）；
3. 与线上 `base.json` 比对，没变就不产生空提交；
4. 变了就通过 GitHub API PUT 提交新的 `base.json`（token 在 `ts-state/.gh_token`）；
5. 推完回读校验，最长等 90 秒，确认 Pages 构建完成。

`boot.sh` 里已挂 `(sleep 20; sh $P/base-sync.sh --watch 300) &`，
**容器重启 / NAS 断联重连后最多 5 分钟自动恢复**，不需要人手动改地址。

> 要彻底不换域名，得上 named tunnel（需自有域名）或 Tailscale Funnel（需 SSO 授权）。
> 这两条都属于「要不要花钱/要不要第三人授权」的决策，当前方案是自愈而不是固定。

## 7. 一键执行入口

### 7.1 首次补齐 / 新增一批照片后

在 `album-node` 容器网页终端里跑（门户 → Docker → 容器 → album-node → 终端 → 新增 → `/bin/sh`）：

```sh
wget -q -O /tmp/nas-setup.sh \
  https://raw.githubusercontent.com/elizond0/album/main/deploy-scripts/nas-setup.sh \
  && sh /tmp/nas-setup.sh > /srv/pub/wb_setup.log 2>&1 &
```

脚本可重入，按顺序做六件事：检查依赖 → 部署 `mkthumb.py`/`base-sync.sh`/`mkindex.py`/`boot.sh`
→ 生成缩略图 → 备份原片并转码 + 抽封面 + 小写化 → 重建 `index.json` → 启动域名自愈常驻。
进度看 `https://<当前隧道>/wb_setup.log`。

### 7.2 只更新内容清单

```sh
python3 build_content.py --nas <隧道地址>/index.json   # 在沙箱里跑，产出 data/content.json
python3 scripts/gen_pages.py                            # 刷新子页与时间戳
git add -A && git commit -m "chore(content): 同步 NAS 清单" && git push
```

`build_content.py` 会把现有 `content.json` 的 `home` / `texts` / `pages` 原样带过来
（`CARRY_KEYS`），**后台调过的行列数不会被重建冲掉**。

### 7.3 依赖

容器基于 `alpine:3.20`，`boot.sh` 里必须装齐：

```sh
apk add --no-cache caddy curl python3 py3-pillow ffmpeg
```

漏了 `ffmpeg` 或 `python3`，`mkthumb.py` / 转码会静默失败 —— 这正是上一版的问题。

## 8. 常见错误对照表

| 现象 | 原因 | 修法 |
|---|---|---|
| 照片全部横躺 | 先删 EXIF 再去方向 | transpose → 丢元信息 |
| 照片偏色 | 广色域 ICC 没转 sRGB | `ImageCms` 转 sRGB |
| PNG 转 JPG 黑底 | 透明通道当黑色 | 白底 `paste(mask=alpha)` |
| **首页打开下 68 MB** | `preload=metadata` + 无 poster | `preload=none` + poster |
| **缩略图生成了却不生效** | 构建写 `s`、前端读 `thumb` | 统一为 `thumb`，前端兼容 `s` |
| **改了 hero 不生效** | `IMG_6914.jpg` vs `img_6914.jpg` | 全链路小写 + `toLowerCase()` |
| 视频发灰 | HLG 没做 tonemap | zscale 滤镜链 |
| 视频能下不能播 | `moov` 在文件尾 | `-movflags +faststart` |
| 站点图片全挂 | 隧道换了域名 | `base-sync.sh --watch 300` |
| 后台改的行列数被冲掉 | 重建时没 carry meta | 保留 `CARRY_KEYS` |

## 10. 两个容易被误判成「代码写错」的前端坑

### 坑一：自托管中文字体把 DOMContentLoaded 拖死

`assets/fonts/` 有 100+ 个 woff2 子集。用 `<link rel=preload>` 全量预加载会拖死首屏。
按页面实际用到的字符子集按需加载，其余交给浏览器懒取。

### 坑二：`.reveal` 依赖 IntersectionObserver

元素初始 `opacity: 0`，靠 observer 回调加 `.is-visible`。
如果 JS 报错或 observer 没建立，整页内容都在但**全透明**，看起来像白屏。
**验证页面「真的看得见」的三条判据**：

1. `document.querySelectorAll('.reveal.is-visible').length > 0`
2. `getComputedStyle(el).opacity === '1'`
3. 截图非空（不能只靠 DOM 文本判断）

另：`content-visibility: auto` 会让屏外卡片跳过布局绘制，
用 `document.querySelectorAll('.wall__item').length` 数出来的是已渲染批次数，不是照片总数。
