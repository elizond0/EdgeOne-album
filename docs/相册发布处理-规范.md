# 相册发布处理规范（规则固化）

> 适用场景：把 NAS 上的原图原片，处理成可公网直链发布的版本。
> 本文是**可执行规则**，不是建议。任何一次处理都必须按这个顺序做，顺序错了结果就是错的。

---

## 0. 三层目录，职责不重叠

| 目录 | 谁在用 | 内容要求 | 挂载方式 |
|---|---|---|---|
| `共享文件夹/Photos/` | UGOS「相册」应用 | **原图原片**，EXIF/GPS/拍摄时间完整保留 | 只给相册应用读 |
| `共享文件夹/照片视频/csy/` | 你上传的暂存区 | 原始文件，不做任何加工 | 容器只读 |
| `共享文件夹/照片视频/album-pub/` | 公网发布 | 压缩去元信息的 JPG + 转码 MP4 + `index.json` | 容器可写 |

**铁律**：`Photos/` 里的文件一个字节都不要改。压缩版只出现在 `album-pub/`，绝不回写。

## 1. 图片处理（六步，顺序不可调换）

### 为什么顺序是死的

iPhone 竖拍的照片，**像素其实是横的**，靠 EXIF 里的 `Orientation=6` 让浏览器转 90°。
如果先清掉 EXIF 再去转方向，方向信息已经没了，照片就全躺下——而且是**批量全躺**，几百张一起错，很难手工修。

所以：**先读日期 → 再烘焙方向 → 最后才丢元信息**。

### 步骤

| # | 动作 | 代码 | 为什么 |
|---|---|---|---|
| 1 | 读 EXIF 拍摄时间 | `exif.get(36867)` 回退 `306`、再回退 mtime | 后面元信息会丢，日期必须提前取出 |
| 2 | **烘焙方向** | `ImageOps.exif_transpose(im)` | 把 Orientation 写进像素，之后删 EXIF 才不会歪 |
| 3 | 统一 RGB | RGB 直通；RGBA/LA/P → 白底合成 | PNG 透明区域直接转 JPG 会变黑底 |
| 4 | 长边缩到 2048 | `im.resize(..., Image.LANCZOS)` | 视觉无损，手机原图 4032px 没必要 |
| 5 | 存 JPEG q85 | `quality=85, optimize=True, progressive=True` | 省 60–75%，progressive 让加载有渐进效果 |
| 6 | 文件名小写 `.jpg` | `stem.lower() + ".jpg"` | 避免 `IMG_1.JPG` 与 `IMG_1.jpg` 大小写不一致导致 404 |

### 第 5 步的隐藏要求

`im.save()` **不要传** `exif=` 和 `icc_profile=` 参数。
PIL 的行为是：不传就不写。传了 `exif=im.info['exif']` 就等于把元信息原样带过去，白做。

### “无损”到底能做到多少

| 方式 | 体积 | 画质 |
|---|---|---|
| `jpegtran -optimize`（真无损） | 只省 5–10% | 像素完全不变 |
| 长边 2048 + q85（本项目采用） | 省 60–75% | 100% 放大才看得出 |

本项目选后者，因为目的是公网加载速度。

## 2. 视频处理（HDR 是必踩的坑）

### 症状

iPhone 拍的视频是 **HLG HDR**（`color_transfer=arib-std-b67`，10bit，`bt2020`，部分带 Dolby Vision）。
直接 `-c:v libx264` 转出来，在普通 SDR 屏幕上**整体发灰、色彩寡淡**——不是编码参数问题，是色彩空间没转换。

### 判断方法

```sh
ffprobe -v error -select_streams v \
  -show_entries stream=color_transfer,pix_fmt,color_primaries \
  -of default=nw=1 文件.MOV
```

`color_transfer=arib-std-b67` 就是 HLG，必须做色调映射。
`pix_fmt=yuv420p10le` 说明是 10bit，10bit 内容压到 8bit 也需要正确映射，否则有断层。

### 正确命令（已验证）

```sh
ffmpeg -y -i in.MOV \
  -vf "zscale=t=linear:npl=100,format=gbrpf32le,zscale=p=bt709,tonemap=tonemap=hable:desat=0,zscale=t=bt709:m=bt709:r=tv,format=yuv420p" \
  -c:v libx264 -crf 20 -preset veryfast \
  -c:a aac -b:a 128k \
  -movflags +faststart \
  -map_metadata 0 -map_chapters 0 \
  out.mp4
```

| 参数 | 作用 |
|---|---|
| `zscale=t=linear:npl=100` | 解 HLG 到线性光，`npl=100` 指定参考白 |
| `tonemap=hable:desat=0` | Hable 曲线压高光，`desat=0` 保留饱和度（否则会褪色） |
| `zscale=t=bt709:m=bt709:r=tv` | 回写 BT.709 / limited range，播放器才认 |
| `format=yuv420p` | 8bit 4:2:0，Chrome/Safari 全兼容 |
| `-movflags +faststart` | moov 前置，网页播放不用下完整个文件 |
| `-map_metadata 0` | **保留 creation_time**（实测输出仍为 `2026-06-20T08:06:48Z`） |

### 为什么不用 `-c copy` 改封装

MOV 里装的是 HEVC，改封装成 MP4 之后 Chrome 依然播不了。**必须重编码**。

### 原片去哪

原片留在 `Photos/`，不覆盖、不删除。H.264 要达到 HEVC 同画质，文件反而更大，覆盖等于用更差的换更好的。

## 3. 常见错误对照表

| 现象 | 原因 | 修法 |
|---|---|---|
| 照片全部横躺 | 先删 EXIF 再去方向 | 顺序换成 transpose → 丢元信息 |
| 照片偏色（红变橙） | 广色域 ICC 没转 sRGB | 编码前 `ImageCms` 转 sRGB |
| PNG 转 JPG 出现黑底 | 透明通道被当黑色 | 白底 `paste(mask=alpha)` |
| 视频发灰 | HLG 没做色调映射 | 加 zscale + tonemap 滤镜链 |
| 视频能下不能播 | `moov` 在文件尾 | `-movflags +faststart` |
| 视频没声音 | `-an` 或音频流没映射 | 保留 `-c:a aac`，不写 `-an` |
| 拍摄时间丢失 | 没加 `-map_metadata 0` | 加上，并验证 `TAG:creation_time` |
| 网页 404（名字对不上） | 大小写差异 | 输出统一小写 |

## 6. 链路上线机制（容器重启后如何自愈）

发布目录里的文件不会自己变得可访问。公网访问依赖一条**自动重建的链路**，全部由 `照片视频/ts-state/boot.sh` 在容器启动时执行：

```text
容器启动
  → apk add caddy curl（重建后是全新层，每次都装）
  → caddy 起 8443 静态服务，root = /srv/pub
  → cloudflared 起快速隧道，指向 127.0.0.1:8443
  → 从 cf.log 抓出新域名
  → 写本地 /srv/pub/base.json
  → sh pub_gh.sh <域名>  推送到 GitHub 仓库根 base.json
  → EdgeOne Pages 感知提交，1–3 分钟重建站点
  → 前端 nas.js 读 base.json 拿到域名，再读 index.json 拿清单
```

### 关键约束

| 约束 | 原因 |
|---|---|
| `docker-compose.yaml` 的 command 只能有一行 `sh -c "sh /var/lib/tailscale/boot.sh"` | 所有逻辑放持久卷，重建容器不会丢 |
| `ts-state/` 必须挂到 `/var/lib/tailscale` | boot.sh、cloudflared 二进制、Caddyfile、`.gh_token` 都在这里 |
| `.gh_token` 权限 `600`，只在容器内 | 不写进仓库、不写进 compose、不出现在文档里 |
| GitHub token 必须有 `Contents: Read and write` | `pub_gh.sh` 要读 sha 再 PUT |
| `base.json` 必须带 `Cache-Control: no-store` | 否则 CDN 缓存旧域名，页面指向已失效的隧道 |

### 换脚本的正确姿势

终端粘贴大文件会被截断，`put.py` 又慢到 5 分钟以上。**最快且可靠的通道是仓库中转**：

```sh
# 1. 沙箱推到仓库（秒级）
python3 gh_put.py pub_gh.sh "deploy-scripts/pub_gh.sh" "chore: 更新推送脚本"

# 2. 容器从仓库拉回（带原始内容头，不用解 base64）
T=$(cat /var/lib/tailscale/.gh_token)
curl -s -H "Authorization: token $T" -H "Accept: application/vnd.github.raw" \
  https://api.github.com/repos/elizond0/EdgeOne-album/contents/deploy-scripts/pub_gh.sh \
  -o /tmp/pub_gh.sh
md5sum /tmp/pub_gh.sh   # 与本地比对，一致再 cp
```

## 7. 站点的数据来源（改动了什么）

EdgeOne 上的「我们的故事」站点原本从 Blob 存储读图（1 GB 上限）。现在的数据流：

| 环节 | 文件 | 行为 |
|---|---|---|
| 拿隧道地址 | `scripts/nas.js` | `fetch("base.json?_=" + Date.now(), {cache:"no-store"})` |
| 拿清单 | 同上 | `fetch(base + "/index.json")` |
| 渲染照片 | `scripts/main.js` → `renderAll()` | 开头 `await window.NAS.load()`，成功后覆盖 `window.PHOTOS` |
| 渲染视频 | 同上 | 覆盖 `window.VIDEOS` |

**唯一改动点**是 `renderAll()` 开头那 8 行；`renderWall` / `renderVideos` 的原有逻辑、样式、灯箱、编辑面板全部不动。

`index.json` 的字段约定（改 `mkindex.py` 时必须保持一致）：

```json
{ "f": "img/img_7913(20260704-133648).jpg", "d": "2026-09-24",
  "w": 1278, "h": 1704, "k": "photo" }
```

`f` 是相对 `album-pub/` 的路径，`k` 取 `photo` / `video`，`d` 是拍摄日期（`YYYY-MM-DD`，缺失时空字符串）。

## 8. 静态托管选型（2026-11-15 实测结论）

**结论：用 GitHub Pages。EdgeOne Pages 中国站对「不买域名」的人不可用。**

### EdgeOne Pages 的死结

官方规则原文：加速区域选「中国大陆可用区」或「全球可用区（含中国大陆）」时，项目域名**只能通过系统生成的预览链接访问，有效期 3 小时，超时返回 401**；选「全球可用区（不含中国大陆）」则**中国大陆网络直接 401**。

想让域名长期可用必须绑自定义域名，而含中国大陆的区域要求 ICP 备案 —— 备案又要求先有境内云服务器。三个条件（免费 / 固定 / 国内可访问）在这条路上不可能同时满足。

> 提醒：控制台里 `console.cloud.tencent.com/edgeone/sites` 是**边缘安全加速**，和 Pages 是两条产品线，别走错入口。Pages 入口是 `console.cloud.tencent.com/edgeone/pages`。

### GitHub Pages 的落地方式

| 项 | 值 |
|---|---|
| 地址 | `https://<用户名>.github.io/<仓库名>/` |
| 前提 | 仓库必须 **Public**（免费账号不支持私有仓库开 Pages） |
| 关闭 Jekyll | 仓库根放一个 `.nojekyll`，否则构建慢且可能报错 |
| 开启方式 | Settings → Pages → Deploy from a branch → main / root |
| API 开启 | `POST /repos/{owner}/{repo}/pages`，body `{"source":{"branch":"main","path":"/"}}` |
| 缓存 | 默认 `max-age=600`，验证新版本要带 `?v=随机数` 绕过 |

## 9. 两个会让人误判成"代码写错了"的前端坑

### 坑一：自托管中文字体把 DOMContentLoaded 拖死

霞鹜文楷按 unicode-range 切成上百个 woff2 分片，`wenkai.css` 210 KB。同步 `<link>` 引入时，`document.readyState` 卡在 `interactive` 长达 20 秒以上，`DOMContentLoaded` 不触发，**main.js 里的渲染回调根本不执行**，照片墙一片空白。

症状极易误判：页面标题、首屏 hero 都正常渲染（那是静态 HTML），只有 JS 产出的内容为空。

**正确做法**：等 `load` 之后再动态注入字体样式表，字体晚到不影响内容。

```html
<script>
  window.addEventListener("load", function () {
    setTimeout(function () {
      var l = document.createElement("link");
      l.rel = "stylesheet";
      l.href = "assets/fonts/wenkai.css";
      document.head.appendChild(l);
    }, 800);
  });
</script>
```

### 坑二：`.reveal` 依赖 IntersectionObserver，不回调就整页透明

样式是 `.reveal { opacity: 0 }` + `.reveal.in { opacity: 1 }`，靠 `IntersectionObserver`（threshold 0.12）加 `in`。在无头浏览器和部分内嵌 WebView 里这个观察器不回调，562 张卡片全部 `opacity: 0`。DOM 节点数、`naturalWidth` 全都正常，**只有肉眼看不见** —— 光看接口返回会误判成"已经好了"。

**正确做法**：加一段按视口位置补 `in` 的兜底，每秒扫一次，只处理视口上下 400px 内的元素（保留滚动渐入效果）。

```html
<script>
  (function () {
    function tick() {
      var h = window.innerHeight;
      var p = document.querySelectorAll(".reveal:not(.in)");
      if (!p.length) return;
      for (var i = 0; i < p.length; i++) {
        var r = p[i].getBoundingClientRect();
        if (r.top < h + 400 && r.bottom > -400) p[i].classList.add("in");
      }
    }
    setInterval(tick, 1000);
    window.addEventListener("load", function () { setTimeout(tick, 200); });
  })();
</script>
```

### 验证页面是否真的"看得见"的三条判据

只看 HTTP 200 会误判，必须同时满足：

1. `document.readyState === "complete"`
2. `document.querySelectorAll('.wall__item').length` 等于照片总数
3. 卡片 `getComputedStyle(el).opacity === "1"`，且截图里能看到真实画面
